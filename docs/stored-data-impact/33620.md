# Stored-data impact: #33620 Account key: Keep two different sign-ins from ever producing the same account key

## Narrowing
From plugin 2.17.0 (Version 1.35, DD-182), hooks-handlers/lib-foundation-key.sh refuses a server
address or a sign-in that holds a control character (bytes 0x00 to 0x1F, or 0x7F) before the account
key is made. A refused identity has no key and is not known, so SessionStart, the per-prompt
Foundation hook and the PreCompact hook deliver and write nothing (the #32915 fail-closed path, with
its existing notice), every name function gives no name, and the Codex start arms no hand-off. The
join the key is hashed over, `<url>\n<key>`, is unchanged, so every valid pair keeps the key it has
today: the two fixed keys pinned in tests/unit/account-key-no-collision.bats were computed from the
unchanged code. Before this, two different pairs whose line break moved the boundary hashed to one key
(33363 QA finding S3).

## Stored records
None are affected. The key names local files only (the Foundation set, the session and per-session
markers, the memories file, the Codex hand-off); nothing is written to the MMRY service and no
database row is read differently. No valid configuration holds a control character: setup writes the
key the service issued (hex) and a plain URL, so no existing account's key, and so none of its local
files, changes. The only configuration this narrows is one edited by hand to hold a control character
in the address or the key; such a session is told, once, that its configuration does not identify the
account and server, as a session with no server address already is, and loads nothing. Its old local
files under the key the previous plugin computed are never read again and go with SessionStart's
seven-day sweep.
No audit query applies: there is no server-side row to count.
