# Stored-data impact: #33617 Codex start: Keep each account's late-start hand-off its own when accounts share a session id

## Narrowing
From plugin 2.15.7 (Version 1.34), the two files that carry a late Codex session start's memories
to the conversation's first prompt are named by the account key as well as the session id:
`.mmry-codex-late.<key>.<sid>` and `.mmry-codex-start.<key>.<sid>.<pid>.{out,ready,pid,claim}`,
the `<key>.<sid>` part being the one every Foundation file has carried since #33363
(`mmry_foundation_session_part_v`, lib-foundation-key.sh). Both early paths compute the key
through hooks-handlers/lib-codex-key.sh (builtins only). The reader, hooks-handlers/
codex-first-prompt.sh, additionally refuses any hand-off whose "Read them now" memories path is not
`mmry-memories.<its own key>.`, clears it, and gives the existing not-loaded notice. Before this,
both files were named by the bare session id (codex-hook.sh, codex-first-prompt.sh), so two MMRY
accounts on one machine sharing a session id could be handed each other's memories path (33363 QA
finding S1).

## Stored records
None are affected. The hand-off and its marker are transient files in the temp folder of the
customer's own machine, written by a session start and removed by the first prompt that collects
them; nothing is written to the MMRY service and no database row, memory, Foundation file or
memories file (`mmry-memories.<key>.<sid>.md`) is renamed, rewritten or read differently. The only
records written under the wider rule are bare-named marker and hand-off files left on a machine
whose conversation was armed by the previous plugin and had not yet reached its first prompt at
the upgrade. Those are never read again (DD-179): the new reader looks only for the keyed name, so
their first prompt says nothing and the late notice the start already gave stands. The existing
twelve-hour sweeps in codex-hook.sh and codex-first-prompt.sh match `.mmry-codex-late.*` and
`.mmry-codex-start.*` and remove them. No audit query applies: there is no server-side row to
count.

## Decision
Leave the bare-named files to the sweep and never read them, by any account, not even once for
the same account (the 33363 plan and brief for #33617, Seat B for release lead 439, 2026-11-09,
applying DD-176's reasoning: "never read a bare name"). A bare-named file carries no account mark,
so nothing in it proves whose it is, and a read-once fallback would be the defect under another
spelling. What a customer expects to keep is their own memories, and they keep them: a running
conversation's memories are the account-keyed memories file, which this change does not touch,
and its first prompt after the upgrade simply gives no late hand-off; the memories are loaded
normally at the next session start, or on request.
