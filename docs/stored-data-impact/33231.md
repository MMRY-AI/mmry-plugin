# Stored-data impact: #33231 Codex start: Keep startup hand-off files private to their owner on shared machines

## Narrowing
From plugin 2.17.0 (Version 1.35, DD-182), the files that carry a Codex session start to the
conversation's first prompt, the late marker `.mmry-codex-late.<key>.<sid>`, the hand-off
`.mmry-codex-start.<key>.<sid>.<pid>.{out,ready,pid,claim}`, the saved payload
`.mmry-codex-start.payload.<pid>` and the two fixed-name logs `mmry-codex-session-start.log` and
`mmry-codex-first-prompt.log`, live in `<CODEX_HOME, else $HOME/.codex>/mmry-handoff`, a folder the
start creates with owner-only permissions (`mkdir -m 700`) only when it is absent, and that both the
start (hooks-handlers/codex-hook.sh) and the first prompt (hooks-handlers/codex-first-prompt.sh) use
only when it is a directory, not a link, and owned by the caller (hooks-handlers/lib-codex-key.sh).
Every file written there is owner-only (`umask 077`). The first prompt also requires the marker, .out
and .ready to be the caller's own regular files, not links. The sh gate in hooks/codex-hooks.json and
codex-hook.cmd look in the new folder. Before this, the same files sat in `${TMPDIR:-/tmp}` with the
invoking umask, where on a shared Linux machine another user could read them, plant a .ready/.out pair
to inject text, or put a link at a path the hook would write through (independent QA of #33062, new
requirement 1).

## Stored records
None are affected. These are transient files on the customer's own machine, written by a session
start and removed by the first prompt that collects them; nothing is written to the MMRY service and
no database row, memory, Foundation file or memories file (`mmry-memories.<key>.<sid>.md`) is
renamed, rewritten or read differently. The memories file itself stays in the temp folder, now
created owner-only (#33652). The only records written under the wider rule are marker and hand-off
files left in the temp folder on a machine whose conversation was armed by the previous plugin and had
not yet reached its first prompt at the upgrade. Those are never read again: neither gate looks in the
temp folder, and the reader looks only in the per-user folder, so their first prompt says nothing and
the late notice the start already gave stands. The sweeps in codex-hook.sh and codex-first-prompt.sh
still match `.mmry-codex-late.*` and `.mmry-codex-start.*` in the temp folder and remove any such file
more than twelve hours old, but only when they run: at a later Codex session start, or at a first
prompt that found a marker in the per-user folder. On a machine where Codex is not started again, the
files stay until the operating system clears its temp folder. Nothing reads them.
No audit query applies: there is no server-side row to count.
